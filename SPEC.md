# Specification

This document states which markdown this library generates, what it deliberately does not generate, and what stays unchanged from v1.0.0 onwards. It is the answer to two questions: "can my generated documents change under me?" and "why does the library not support feature X?".

## Target specification

The library targets [GitHub Flavored Markdown](https://github.github.com/gfm/) (GFM), which is the markdown GitHub renders in repositories, issues, and pull requests. On top of the GFM core the builders emit these GitHub extensions:

- [Alerts](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#alerts): `> [!NOTE]`, `> [!TIP]`, `> [!IMPORTANT]`, `> [!WARNING]`, and `> [!CAUTION]`.
- [Mermaid diagrams](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams#creating-mermaid-diagrams), written as a fenced code block tagged `mermaid`. The `mermaid/*` subpackages build the contents of such a block.
- [Footnotes](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#footnotes): `[^1]` references and `[^1]: text` definitions.
- [Mathematical expressions](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/writing-mathematical-expressions): `$inline$` and `$$block$$`.
- [Task lists](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/about-task-lists): `- [ ]` and `- [x]`.
- Raw HTML, in exactly one place: `Details` emits a `<details>` element, because markdown has no collapsible section of its own.

Two helpers fall outside GFM and are documented here so their behavior is not mistaken for a GFM guarantee:

- `Highlight` emits `==text==`. GitHub does not render this; Obsidian, Bear, and several static site generators do. It is kept because it has always been part of the API and it costs nothing, but it is not part of the GFM target.
- The badge helpers (`RedBadge` and friends) emit an image link pointing at `img.shields.io`. The markdown is plain GFM; what the image looks like is up to that external service.

Mermaid diagram bodies follow [the mermaid syntax](https://mermaid.js.org/intro/syntax-reference.html) rather than GFM, since a markdown parser treats them as opaque code block content. Diagram titles are emitted as a YAML front matter block inside the diagram, which is how mermaid itself expects them.

## Out of scope

The following are not supported, and will not be added. This is a design decision, not a backlog: the value of this library is that a document is a single method chain that a reader can follow top to bottom, and every item below would replace that chain with a tree.

- **Nested block structures.** Lists inside list items, tables inside lists, blockquotes inside tables, and fenced blocks inside list items. The builders emit one block per call at the top level of the document.
- **Arbitrary CommonMark or third party extensions.** Definition lists, abbreviations, admonition syntaxes other than GitHub alerts, front matter for the document itself, and templating hooks.
- **General HTML passthrough helpers.** `Details` exists because collapsible sections have no markdown form. Callers who need other HTML can pass it to `PlainText`, and it is their responsibility.
- **Parsing or rendering markdown.** This library only writes markdown. It does not read it, and it does not convert it to HTML.

A feature request that lands in this list is closed with a link to this section. When markdown itself gains something, or mermaid ships a new diagram type, that is a different matter: adding a diagram type is additive and stays within the design.

## Output stability

From v1.0.0 onwards the exact bytes each builder produces are part of the public contract. Users regenerate documents from this library, so an output change lands in their repositories as a diff.

- Every existing builder method keeps producing byte-for-byte identical output across v1.x releases.
- The only exception is output that is objectively wrong: markdown that GitHub does not parse as the call intended, or a mermaid diagram that the mermaid renderer refuses to draw. Such a fix ships in a patch release with the reasoning in `CHANGELOG.md`.
- Output is pinned by golden files under `testdata/golden/` in every package, so any change to the generated bytes fails the test suite rather than reaching a release.

### Line endings

The output uses the line ending of the platform the program runs on: `"\n"` on Linux and macOS, `"\r\n"` on Windows. This is deliberate, since generated files are usually written straight to disk on the machine that builds them. It also means the same program produces different bytes on different platforms, so tests that compare generated output byte for byte need a platform split, and golden files should be compared after normalizing line endings.

`Build` also guarantees the document ends with a line ending. markdownlint's MD047 requires it, and without it a second document appended to the same writer would splice its first line onto the last line of the first one.

## API stability

The exported Go API follows [semantic versioning](https://semver.org/).

- v1.x releases only add exported identifiers. Nothing exported is removed, renamed, or given a different signature.
- A design mistake that cannot be fixed without breaking callers stays, and is marked with a `// Deprecated:` comment pointing at the replacement. The deprecated identifier keeps working.
- Everything under `internal/` is not part of the API, and Go's own tooling enforces that.

## Supported Go versions

The `go` directive in `go.mod` names the oldest Go release this library builds with. Continuous integration runs the test suite against that release and the two after it, on Linux, macOS, and Windows.

Raising the `go` directive is a minor release, not a major one: it does not change the API, and Go's module resolution deals with a user on an older toolchain by selecting an earlier version of this library.

## Known behaviors

These are contracts rather than accidents, and are covered by tests:

- A builder records the errors it encounters while the chain runs and returns them from `Error` and from `Build`. Nothing in the chain panics on bad input, and no call has to be checked individually.
- `Build` with a nil writer returns an error rather than panicking.
- `String` returns the document built so far whether or not an error occurred, so it works on a builder that never had a writer. This is how the `mermaid/*` subpackages hand a diagram to `CodeBlocks`.
